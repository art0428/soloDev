# 管理者工作室 AI 單人開發手冊 v1.1

> 這本手冊給一個人用。你負責想清楚要做什麼、畫出原型、做決定、驗收；寫程式、寫測試、寫文件、跑檢查都交給 AI（Claude Code）。
> 手冊只講三件事：每一步做什麼、怎樣算做完、給 AI 的話怎麼說。細部規則（AI 能動什麼、不能動什麼、用什麼指令驗證）寫在專案的 CLAUDE.md，手冊不重複。

---

## 0. 怎麼用這本手冊

1. 先做好前台原型 index_v1.html（第 4 章說要包含什麼）。沒有原型不要開工，AI 會自己猜。
2. 用 studio-init 初始化程式建專案（第 6 章步 0），手冊副本會自動放進 docs/，CLAUDE.md 會指向它，Claude Code 開工就會讀。
3. 照第 6 章步 0〜6 把第一版做出來、上線。
4. 之後每個新需求、每個 bug，都照第 7 章「切片五步」做一輪。
5. 第 9 章的正式機規則與第 10 章的持續優化，是系統上線後每天要守的事。

名詞一律在第一次出現時用一句話解釋；全部名詞整理在第 12 章。

## 1. 前提、角色與節奏

**前提**：你已經把前台原型做好，並且自己在瀏覽器裡把每個功能點過一遍。原型就是需求來源。

**角色**：只有一個人，但要戴三頂帽子，而且**每次只戴一頂**：

| 帽子 | 做什麼 | 什麼時候戴 |
|---|---|---|
| 需求帽 | 畫原型、寫拍板紀錄、決定要不要做 | 開新切片之前 |
| 工程帽 | 下 Prompt、看 AI 回報、看測試結果、合併 | 切片 A〜D |
| 驗收帽 | 用真實帳號照原型驗、決定過不過 | 切片 E、上線前 |

為什麼要分：一個人最容易犯的錯是「邊做邊改需求」，AI 做到一半你又說要改，最後誰都說不清楚現在的規格是什麼。帽子分開，需求改了就回到需求帽、出新版切片原型、寫一條拍板紀錄，再回來。

**AI 對話的角色**：Claude Code 的每一個對話視窗是一個「對話」。你會同時有幾種對話，各有各的權限：

| 對話 | 做什麼 | 碰不碰正式機 |
|---|---|---|
| 開發對話 | 一個切片一個對話，做 A〜D | 不碰 |
| 部署對話 | 唯一能碰正式機的對話，做備份、migration、部署、更新現況表 | 只有它碰 |
| 夜間守衛 | 排程每天凌晨跑全套測試與 E2E，紅了就出報告 | 不碰 |

**節奏一句話**：先把原型功能全部做出來上線（第 6 章），之後一個切片一個切片優化（第 7 章）；上線後每天夜間自動跑一次全套（第 10 章）。

## 2. 技術架構

新專案一律用這一套。它不是最酷的，是最適合「一個人配 AI」的：每一層都讓 AI 寫起來少出錯、讓檢查工具抓得到錯。

| 層 | 技術 | 為什麼選它 |
|---|---|---|
| 前台 front/ | React＋Vite＋TypeScript＋React Router | React 是畫面函式庫；Vite 是打包工具，建置快設定透明；TypeScript 有型別檢查，契約一改前端立刻紅 |
| 後端 backend/ | Node.js（最新 LTS）＋Fastify＋TypeScript＋Prisma | Fastify 是後端框架；Prisma 是資料庫工具，schema 一份、migration 自動 |
| 資料庫 | PostgreSQL | 本機開發用本機，正式用 Cloud SQL |
| 後台 admin/（選配） | Fastify＋EJS 伺服器渲染，直接用 Prisma 讀寫，不經 API | 後台多是查詢維護，伺服器直接吐 HTML 最簡單，AI 寫得又快又少錯；攻擊面也小 |
| 契約 | OpenAPI 3（api/openapi.yaml）→ 自動產生 packages/api-client | 前台只能呼叫契約裡有的 API |
| 登入 | MCC（members.managers.center）OIDC，BFF 模式 | 瀏覽器只導向 MCC，Token 由後端換、存 httpOnly Cookie，前端不碰 Token。這是前一個專案資安稽核第一名弱點換來的選擇 |
| 設計規範 | 管理者工作室設計系統 https://art0428.github.io/webdesign/ | 選一套風格（S1〜S7）開發，元件不寫死顏色 |
| 部署 | Docker＋GCP：前台靜態檔放 Cloud Storage＋CDN、backend 與 admin 各一個 Cloud Run、密鑰放 Secret Manager | 部署來源是本地資料夾（gcloud builds submit），不是 GitHub |
| 套件管理 | pnpm | |

**後台什麼時候做**：前台第一版上線後。很多系統根本不需要後台，先問自己「管理員要做的事能不能在前台用管理員角色做掉」，能就不做後台。

由 studio-init 一次建好。文件放 docs/，程式放各自資料夾，測試跟程式放一起。

```
project/
├── CLAUDE.md                        ← AI 的規則：能動什麼、不能動什麼、用什麼驗證（專案資訊四行要填）
├── README.md                        ← 程式架構與啟動方式
├── docs/
│   ├── 管理者工作室AI單人開發手冊.md   ← 本手冊副本
│   ├── prototype/
│   │   ├── index_v1.html            ← 前台完整原型（凍結，不回頭改）
│   │   ├── admin_v1.html            ← 後台原型（選配，前台上線後才做）
│   │   └── slices/<切片名>_vN.html   ← 切片原型：之後每次只畫要改的畫面
│   ├── decisions.md                 ← 拍板紀錄：每個決定一行、有編號（D1、D2…）
│   ├── PROGRESS.md                  ← 進度板：進行中的切片、待驗收、修正清單、技術債
│   ├── DEVLOG.md                    ← 工作日誌：每次對話收工一筆
│   ├── ui-terms.md                  ← 畫面用語詞彙表：同一件事全站同一個名字
│   ├── test-baseline.md             ← 測試基準：最近一次全套的題數
│   └── requirements/seo-pages.md    ← 需要 SEO 的公開頁清單（沒有就寫「無」）
├── api/openapi.yaml                 ← API 契約（唯一事實來源；範本附登入、/api/me、/health 骨架）
├── front/src/                       ← 前台：pages/<模組名>/、components/；測試 *.test.tsx 同目錄
├── admin/src/                       ← 後台（選配）：auth/、pages/<模組名>/、layouts/
├── backend/src/                     ← 後端：auth/ routes/ controllers/ services/ repositories/ lib/dates.ts
├── backend/prisma/                  ← schema.prisma、migrations/、seed.ts（schema 唯一來源）
├── backend/scripts/                 ← run-tests.sh、backfill-<主題>.ts、smoke-test.sh
├── packages/api-client/             ← 由契約產生，不手改
├── tests/                           ← 跨模組：contract/ e2e/ security/
├── deploy/                          ← Dockerfile、cloudbuild.yaml、部署說明.md（含正式機現況表）、環境變數名稱清單（值不放這裡）
├── scripts/                         ← init.sh、verify-env.sh、check-contract-drift.mjs、git-hooks/pre-commit
├── .github/workflows/check.yml      ← 只做檢查不部署：lint → typecheck → 契約 → 單元測試 → 密鑰掃描 → 相依漏洞
└── .claude/
    ├── skills/dev-guidelines/       ← 做法與踩坑紀錄（AI 動程式前先讀；你說「放入 skill」就是加一條）
    ├── skills/nightly-guard/        ← 夜間守衛的程序
    ├── skills/mcc-integration/      ← MCC 串接摘要
    └── agents/qa-reviewer.md        ← 獨立 QA 審查員（唯讀，只出報告）
```

**東西放哪裡**：

| 東西 | 放哪裡 |
|---|---|
| 需求 | docs/prototype/index_vN.html、slices/ |
| 決定 | docs/decisions.md（一行一個 D 編號） |
| 進度 | docs/PROGRESS.md |
| 正式機現在是哪一版 | deploy/部署說明.md 的現況表＋git tag |
| 做法與教訓 | .claude/skills/dev-guidelines/SKILL.md |
| 畫面用語 | docs/ui-terms.md |

**切片名 不等於 資料夾名**：切片是開發的一輪，模組是程式的歸屬。資料夾照模組命名（pages/products/），切片名只用在切片原型檔名與 PROGRESS.md。

## 4. 原型怎麼做才夠用

原型是一個可以在瀏覽器點的 index_v1.html。缺任何一項，AI 就會自己猜：

1. **系統說明**：這是什麼系統、給誰用、有哪些角色。
2. **功能清單與優先順序**：這就是切片清單，決定開發順序。
3. **每個功能的畫面與操作流程**：可以實際點。
4. **欄位與驗證規則**：必填、格式、長度、選項。
5. **測試資料**：正常、空白、錯誤三種情境，直接寫在原型裡。
6. **角色與權限**：哪個角色看得到、做得了什麼。
7. **需要 SEO 的公開頁**：寫進 docs/requirements/seo-pages.md，沒有就寫「無」。

※ **示範資料一律虛構、通俗**：原型、測試、使用說明、示範影片裡的公司、客戶、產品、電話、地址、統編，不可以用真實公司、真實品牌或你自己公司的資料。初始化程式會放一份「示範世界」（例：文具批發商「禾木文具」賣給補習班與咖啡館），全專案共用，並有守衛測試擋真實資料。

**凍結規則**：你自己在瀏覽器操作過全部功能、沒有待決問題後，存成 docs/prototype/index_v1.html 凍結，不回頭改。

**切片原型**：第一版之後的需求變更不改完整原型。先戴需求帽跟 AI 討論，再讓 AI 做一個只畫要改的畫面的小原型，存 docs/prototype/slices/<切片名>_v1.html；再改就另存 v2，舊檔不動。同一個畫面同時出現在完整原型與切片原型時，以切片原型最新版為準。

**拍板紀錄**：討論中每個決定寫一行進 docs/decisions.md，給編號（D1、D2…），格式「D12｜2026-11-01｜付款條件改必填，舊單只在送審時擋、存草稿不擋」。之後 PR 描述、測試名稱、commit 訊息都引用編號。這是一個人開發最重要的文件：三個月後你一定忘記為什麼這樣做。

## 5. 參數準備

所有密鑰只放伺服器端的 backend/.env、admin/.env（本機）或 GCP Secret Manager（正式），不進前端、不進 git、不貼進任何對話。

| 參數 | 用途 | 誰提供 |
|---|---|---|
| MCC_CLIENT_ID | 本服務在 MCC 的識別碼（suuid） | MCC 管理者，測試與正式各一組 |
| MCC_CLIENT_SECRET | 後端向 MCC 換 Token 用 | MCC 管理者 |
| MCC_GROUP_JWT | 後端呼叫 /member/check 驗 Session 用 | MCC 管理者 |
| MCC_SERVICE_CODE | X-Service-Code header | MCC 管理者 |
| MCC_REDIRECT_URI | 登入後跳回的網址，須事先在 MCC 白名單登記，一字不差 | 你定、MCC 管理者登記 |
| DATABASE_URL | PostgreSQL 連線字串 | 你（本機）／GCP（正式） |
| SESSION_SECRET | Cookie Session 加密，至少 32 字元隨機字串 | AI 產生、你確認 |
| AUTH_MODE | mcc（真實登入）或 mock（假登入，只准本機與測試） | AI 產生、你確認 |
| FRONT_URL、ADMIN_URL | 登入後導回與 CORS 允許 | AI 產生、你確認 |
| BUSINESS_TZ | 業務時區的 IANA 名稱（例 Asia/Taipei） | 你 |

MCC 憑證只有兩套：開發與測試共用一套（測試 Group），正式機用另一套（正式 Group）。MCC 網址都一樣，靠 Group 憑證區分。每個環境的 redirect_uri 都要登記到對應 Group 的白名單。

**準備完成的檢查**（專案建好後做）：.env 照 .env.example 填齊 → pnpm install && pnpm dev 能跑 → 用測試帳號在本機真實登入成功。

## 6. 啟動階段：從原型到第一版上線

只做一次（有後台的話前台、後台各跑一次）。之後的修正與新需求都走第 7 章。

```
0 初始化 → 1 骨架 → 2 全系統契約 → 3 第一版（原型功能全部實現）→ 4 完整測試 → 5 第一版驗收 → 6 合併 main、打 tag、上正式
```

每一步的「做什麼」是工作內容、「完成」是怎樣算做完、灰色方塊是給 AI 的 Prompt：整段貼進 Claude Code。Prompt 三行依序是：先讀哪些檔、這步做什麼、做完回報什麼。

### 步 0｜初始化（你手動做）

1. 建一個空資料夾，在裡面開 Claude Code，說「初始化專案」（studio-init 會建第 3 章的全部結構，附手冊副本、CLAUDE.md、openapi 骨架、登入程式、users/roles 資料表、示範世界、守衛測試、pre-commit、check.yml）。
2. 把 index_v1.html 放進 docs/prototype/。
3. 執行 bash scripts/init.sh <專案名>：填專案名、檢查原型與第 5 章參數是否齊全、pnpm install、設定 git hooks。
4. 填好 CLAUDE.md 的專案資訊四行（專案名、一句話說明、業務時區、正式網址）。

**完成**：第 5 章的準備檢查通過。

### 步 1｜骨架

**做什麼**：接上登入（真實連 MCC；/api/me 回名稱、頭像、角色；第一次登入自動建檔）、做前台選單（依角色顯示、照原型功能清單排，點進去先是空頁）。不碰業務邏輯。

**完成**：本機真實登入 → 看到自己的名字和該角色的選單 → 每個選單點得進空頁 → 登出。pnpm test、pnpm build 綠。

```
讀 CLAUDE.md 與 docs/prototype/index_v1.html 的系統說明、功能清單與角色。
依手冊步 1，接上登入、使用者資料、前台選單與依角色顯示，不寫業務邏輯。
做完貼 pnpm test、pnpm build 的結果與真實登入後的畫面截圖。
```

### 步 2｜全系統契約（原型 → API 規格）

**做什麼**：在 openapi.yaml 骨架上，從原型的每個畫面、欄位、操作、角色，一次補齊所有業務 API，再 pnpm openapi:gen 產生 packages/api-client。這是第一版的地圖。

**完成**：原型每個操作都對得到一支 API；openapi:lint、typecheck 通過；你看過「畫面 → API」對照表沒有遺漏。

```
讀 CLAUDE.md、docs/prototype/index_v1.html 全部畫面與測試資料、api/openapi.yaml（骨架：登入、/api/me、錯誤格式，不要重寫）。
依手冊步 2，在骨架上從原型推出全部業務 API 補進 openapi.yaml，含 Schema、錯誤碼、分頁、角色；每支 API 的描述要寫清楚誰能打、什麼情況回 403／422。
做完貼 openapi:lint 與 typecheck 結果，並列出「畫面 → API」對照表給我確認。
```

### 步 3｜第一版：原型功能全部實現

**做什麼**：照原型功能清單順序，每個切片跑一輪「切片五步」的 A→D（第 7 章；第一版不做 E 驗收）。切片之間不等驗收，做完直接下一個。

**分批**：原型超過 8 個畫面或 15 支 API，就按模組分批。每批做完先跑步 4（測這批）與步 5（你驗這批），「擋上線」的項目當批修掉再開始下一批；全部批次做完再跑一次完整的步 4，然後步 6。

**完成**：功能清單上的切片全部合併 main，CI 檢查全綠。

**Prompt**：用第 7 章的 Prompt，每個切片分兩次貼。

### 步 4｜完整測試

**做什麼**：第一版切片全部做完後，對照原型功能清單把測試補齊並完整跑一輪：每支 API 的契約測試、每個功能一條 E2E、跨功能流程、密鑰與相依掃描。切片五步只測單一切片，這步補整體與跨切片的部分。

**完成**：pnpm test、pnpm e2e 全綠；每支路由都被測試呼叫過且在契約裡（pre-commit 會擋）；原型功能清單每一項都對得到至少一條測試；未覆蓋項目列出來給你確認。把題數寫進 docs/test-baseline.md。

```
讀 CLAUDE.md、docs/prototype/index_v1.html 的功能清單、api/openapi.yaml、tests/。
依手冊步 4，對照功能清單補齊測試：每支 API 的契約測試、每個功能一條 E2E、跨功能流程，然後完整跑一輪 pnpm test 與 pnpm e2e。
做完用表格貼全部測試結果（哪一端、幾題、幾過），寫進 docs/test-baseline.md；紅燈只准改實作不准改測試；列出未覆蓋項目給我確認。
```

### 步 5｜第一版驗收，列修正清單

**做什麼**：戴驗收帽。用真實帳號把前台整體操作一遍，對照原型列出要修的。AI 整理成修正清單寫進 docs/PROGRESS.md：合併重複、標對應原型區塊與驗收條件、排優先順序，每項標「擋上線」或「上線後修」。要改畫面的做成切片原型。

**完成**：「擋上線」全部用切片五步 A→E 修完、你確認，即為驗收通過；「上線後修」留給第 7 章。

```
讀 CLAUDE.md、docs/prototype/index_v1.html，以及我貼的驗收問題清單。
依手冊步 5，整理成修正清單寫進 docs/PROGRESS.md：合併重複、標對應原型區塊與驗收條件、排優先順序，每項標「擋上線」或「上線後修」，標出哪些需要切片原型。
做完貼清單給我確認。
```

### 步 6｜合併 main、打 tag、上正式

**做什麼**：步 4 全綠、步 5 驗收通過後，開一個**部署對話**，照第 9 章的部署程序上正式：備份、migration、部署、打 tag（v1.0.0）、更新現況表、斷線。

**前置（你先做）**：向 MCC 管理者取得正式 Group 憑證；正式網址登記到正式 Group 白名單；正式環境的 Secret Manager 填好。

**完成**：main 上有 tag，正式環境跑的是這個 tag，正式網址真實登入成功；PROGRESS.md 記下上線版本與「上線後修」清單；deploy/部署說明.md 現況表已更新。

```
讀 CLAUDE.md、docs/PROGRESS.md、deploy/部署說明.md。
依手冊第 9 章部署程序，確認 pnpm test 與 pnpm e2e 全綠、工作目錄乾淨後，逐步執行：備份 → 查 pending migration → migrate deploy → 部署後端 → 部署前端 → 煙霧測試 → 打 tag v1.0.0 → 更新現況表 → 斷開正式庫連線。每一步做完停下來貼結果再做下一步。
```

### 後台（選配）｜前台上線後再做

前台第一版上線後才開始。先做後台原型 docs/prototype/admin_v1.html，再照下表跑步 1〜6，步 0 不重做。會改 schema 或 migration 的切片一次只做一個，先在 PROGRESS.md 登記再動工。

| 步 | 後台怎麼做 |
|---|---|
| 1 骨架 | admin/ 的首頁與選單，沒有 admin 角色的帳號被擋 |
| 2 資料對照 | 後台不經 API、不改 openapi.yaml。改列「後台頁面 → 用到的資料表與欄位」對照表，缺的欄位討論後再加 migration |
| 3 第一版 | 每個切片跑切片五步 B（先寫資料讀寫的測試）→ C（後台頁面）→ D；沒有契約，A 略過 |
| 4 完整測試 | 每個後台功能一條 E2E，後台頁面用 inject() 驗 200／302／403 |
| 5 驗收 | 用有 admin 角色的帳號驗 |
| 6 上線 | 同前台步 6，後台服務不掛公開網域 |

## 7. 迭代階段：切片五步

切片＝一個使用者用得到的完整功能，從畫面、API、後端到資料庫整條做完。每個切片走同樣五個動作，一個切片一次對話。第一版（步 3）跑 A→D，迭代階段跑 A→E。

```
A 契約 → B 後端（先測試再實作）→ C 前台／後台畫面 → D 合併 main → E 驗收
```

### 開始之前：需求帽

畫面有變就先做切片原型（第 4 章）；每個決定寫進 docs/decisions.md 給編號。沒有這兩樣不要開 A。

### A｜契約

- **做什麼**：第一版時確認此切片的 API 區段完整；優化時先改 openapi.yaml 再改程式，改過就 pnpm openapi:gen。
- **破壞性變更先討論**：新增必填欄位、選填改必填、驗證變嚴、權限收緊、schema 改型別，符合任一條就是破壞性變更，要先寫一條拍板紀錄決定「既有資料怎麼辦」（見 B）。
- **完成**：openapi:lint、typecheck 通過。

### B｜後端：先測試再實作

- **做什麼**：先寫會失敗的測試（每端點 200／401／403／422／404；修 bug 時先補一個重現問題的測試），停下來給你確認清單，你說 OK 再實作到全綠，補 migration 與 seed。
- **測試要真的有效**，三條鐵則：
  1. 失敗路徑優先，成功路徑綠了不算回歸保護。
  2. 守衛型測試（掃原始碼擋某種寫法的）寫完要塞一行違規進去確認它會紅。
  3. 修 bug 的重現測試要在修復前先紅過；寫完拿掉修復再跑一次，不紅等於沒寫。
- **破壞性變更三件事**：(1) 補一條「舊資料」測試，用 prisma 直接寫出不符合新規則的資料，**不准改建資料樣板來符合新規則**（那會把舊資料案例從測試裡刪掉）；(2) 明確決定既有資料怎麼辦，三選一寫進 commit 訊息：寫回填腳本、只在往前走的動作上檢查、接受人工補但畫面要指出是哪一欄；(3) 回報時說明影響面。
- **migration 規則**：只新增欄位或資料表、全部 nullable 或帶預設、免回填可上線；會刪東西的 migration 另開一個檔，檔頭寫「先部署程式再跑」。
- **回填腳本**：backend/scripts/backfill-<主題>.ts，不帶參數＝試跑只報數字、--write 才寫、冪等、無來源留 NULL。
- **時間**：事件時刻（歷程、建立、寄出）存 UTC、API 回 ISO 8601、前端依觀看者時區顯示；業務日期（單號、報價日、到期、統計）以 BUSINESS_TZ 計算成純日期字串。後端不可把時刻格式化成字串存起來、不可用 new Date().getHours() 做業務判斷、不可用固定 +8。全部函式只在 backend/src/lib/dates.ts 與 front/src/lib/datetime.ts 這兩個檔。測試環境 TZ 釘成 UTC，刻意不等於業務時區。
- **完成**：pnpm test 全綠、lint、typecheck 通過。

### C｜前台／後台畫面

- **前台**：照原型做 React 畫面，接 packages/api-client。**每個畫面**處理 loading、空白、錯誤、401、403。
- **處理中四件事**：任何會呼叫後端的按鈕一律做滿：(1) 處理中反灰擋重入；(2) 顯示轉圈；(3) 文字換成「儲存中…」這類；(4) 成功才關視窗、失敗留在原地。只有圖示沒文字的小按鈕可省略文字；點下去畫面當場就變的樂觀更新控制項可省略轉圈。
- **用語**：畫面上的名詞照 docs/ui-terms.md，同一件事全站同一個名字；新名詞先加進詞彙表再用。
- **每個畫面一條掛載煙霧測試**（空資料 → 有資料渲染一輪）；互動測試（點了接鍵盤、焦點、打字）用 user-event 不用 fireEvent。
- **各寫一條 E2E**，測試案例對得上切片的驗收條件：原型上每個操作、每個欄位驗證、401／403 各有一條。E2E 一個測試檔一個 seed 帳號，beforeAll 建資料要冪等。
- **後台**：照原型在 admin/ 做模板頁（路由＋EJS＋表單），直接 Prisma 讀寫，不經 API。
- **完成**：元件／頁面測試、E2E 通過，pnpm build 成功。

### D｜合併 main

- **做什麼**：在 claude/<切片名> 分支上做完，動到那一端跑**完整**測試（後端整套、前端整套＋lint；沒動到的那一端不跑），全綠才 git merge --no-ff 回 main。commit 訊息中文、寫清楚做了什麼與為什麼、引用 D 編號。
- **測試三層**，省時間也省 token：
  1. 改動中：只跑跟這次改動相關的測試檔。
  2. 併回 main 前：動到的那一端跑完整。
  3. 全套＋整套 E2E：留給每天凌晨的夜間守衛（第 10 章）。開發對話把寫好或改好的 E2E 檔記進 PROGRESS.md「待夜間跑」。
- **push 與部署一律等你指示**。AI 不自己 push、不自己部署。
- **合併後三件事**：PROGRESS.md 把該切片標「待驗收」並標驗收等級（下一段）；DEVLOG.md 加一筆；如果修到的 bug 正式機也有，回報時必須寫「※ 此修復影響正式機，建議評估熱修」。
- **完成**：main 上 CI 檢查全綠、PROGRESS.md 已標待驗收。

### E｜驗收（分級）

一個人驗不完每一個分支，所以每個切片在 D 就要標等級：

| 等級 | 什麼情況 | 誰驗 |
|---|---|---|
| 親驗 | 新功能、流程改變、權限改變、金額計算、任何使用者會看到差異的 | 你戴驗收帽，在拋棄式環境用真實帳號照切片原型驗 |
| AI 自驗即可 | 文案修正、純樣式、重構、純後端不影響畫面 | AI 用 scripts/verify-env.sh 起拋棄式環境，用真滑鼠真鍵盤操作一遍、截圖附在報告，你事後看 |

- 驗收用 scripts/verify-env.sh start 起一組拋棄式資料庫與前後端（附一家示範公司、一個管理員、一個一般成員），用完 stop 整組刪掉。**不在開發用的資料庫上按會寫入的東西。**
- 沒過 → 回 B 先補失敗測試重現，再修。通過 → PROGRESS.md 勾掉、排進部署清單（第 9 章）。

### 給 AI 的 Prompt（每個切片分兩次貼）

第一次（A＋B）：
```
讀 CLAUDE.md、.claude/skills/dev-guidelines/SKILL.md、api/openapi.yaml 的〈切片名〉區段、docs/prototype/slices/〈切片名〉_vN.html（第一版改讀 index_v1.html 的對應畫面）、docs/decisions.md 的 D〈編號〉。
依手冊切片五步 A、B：先確認或修改契約，再只寫〈切片名〉後端的失敗測試（每端點 200／401／403／422／404；有破壞性變更就加舊資料測試），寫完停下來給我確認；我說 OK 後實作到全綠，補 migration 與 seed。
做完用表格貼測試結果（哪些檔、幾題、幾過），並說明既有資料怎麼辦。
```

第二次（C＋D）：
```
讀 CLAUDE.md、docs/prototype/slices/〈切片名〉_vN.html、packages/api-client、docs/ui-terms.md。
依手冊切片五步 C、D：做〈切片名〉的前台畫面接上 api-client，處理 loading／空白／錯誤／401／403，按鈕做滿處理中四件事，每個畫面一條掛載測試，寫一條對得上驗收條件的 E2E；然後跑動到那一端的完整測試，全綠就 merge --no-ff 回 main，不要 push。
做完貼完整測試結果表、合併的 commit、PROGRESS.md 標的驗收等級；E2E 記進待夜間跑。
```

### 問題從哪裡修

| 問題 | 做法 |
|---|---|
| 畫面或流程要改 | 做切片原型新版號，寫拍板紀錄，走切片五步 |
| 前台用的 API 要改 | A 先改契約；破壞性變更先寫拍板紀錄 |
| 功能 bug | B 先補失敗測試重現，再修；正式機也有的標熱修 |
| 登入、權限、MCC 異動 | 改 backend/src/auth/，改完跑一次真實登入 E2E |
| 建置、部署、憑證 | 看 CI 輸出；憑證在 Secret Manager 改 |
| 文案用語 | 直接改併回，附前後對照表，你事後看 |

### Prompt 三原則

1. **指檔案不貼內容**：告訴 AI 去讀哪個檔，不把檔案內容複製進對話。
2. **一次一步或一個切片**。
3. **最後一定寫「怎樣算對」**：要它貼什麼結果、用什麼格式。

## 8. 多個對話同時做事的規則

一個人常會同時開兩三個開發對話。可以，但要守這幾條，每一條背後都是前一個專案踩過的坑：

1. **一個切片一個分支一個對話**。開工先 git branch --show-current 確認自己在哪個分支；commit 後看訊息裡的 [分支名] 是不是自己的。
2. **別人未提交的檔一律不碰**。git status 看到不是自己的檔，當作不存在。
3. **改 schema.prisma 的切片一次只准一個**，先在 PROGRESS.md 登記再動工。改完 prisma generate 會讓正在跑的開發伺服器立刻吃到新程式，資料庫卻還沒新欄位，整片 500；所以改 schema 的對話要先講一聲，或在隔離副本做。
4. **併回 main 用 merge --no-ff**，別人先推進了 main 就先 rebase 或重新合併，不要 force。
5. **隔離副本一律用絕對路徑**；副本的 node_modules 用實體複製不用符號連結（.gitignore 擋不住連結，會被 add -A 收進版控）。
6. **夜間守衛專門抓「各自綠、合起來紅」**：這是多對話並行的代價，所以第 10 章那一輪不能省。

## 9. 上線與正式機規則

這一章是前一個專案用四次事故換來的，每一條都要照做。**只有部署對話碰正式機，任何正式機狀態變更都要你當次允許**，唯讀查詢可以。

### 9.1 部署前

1. 工作目錄乾淨且已 commit（部署抓的是本地資料夾內容）。
2. 動到那一端全套測試全綠，夜間守衛最近一輪全綠。
3. **臨場重查 pending migration**：npx prisma migrate status 經 cloud-sql-proxy 連正式庫，不可沿用舊盤點（8/28 事故：以為沒新 migration，部署後讀取 500 十五分鐘）。
4. **備份正式庫**到 gcp/db/backup/（已 gitignore）。
5. 列出這次要上的清單，每項標：migration 有無、是否破壞性、要跑的回填腳本、部署後要驗的功能。

### 9.2 部署順序

```
備份 → 只新增的 migration（migrate deploy）→ 部署後端 → 部署前端 → 煙霧測試 → 登入後功能驗證 → 打 tag → 更新現況表 → 斷線
```

- **破壞性 migration（刪欄、刪表）順序相反**：先部署程式、確認穩定，再跑 migration。否則舊 revision 還在讀那一欄會 500。順序寫在 migration.sql 檔頭。
- 前端的 API 網址是建置期燒進去的，改網址要重新 build。
- 回填腳本在部署後手動跑，先不帶參數試跑看數字，再 --write。

### 9.3 部署後

1. **煙霧測試**（/health、幾支公開端點）。
2. **登入後功能驗證**：你登入、AI 操作這次上線的每個功能走一遍。煙霧測試看不到登入後的畫面崩潰。
3. **打 git tag**：prod/vN 打在部署的 commit 上。tag 是「正式機是哪一版」的第二權威。
4. **更新 deploy/部署說明.md 現況表**，當下更新、不拖：最後部署時間、revision、對應 commit、migration 高水位、backfill 已跑、備份檔、部署後驗證結果、repo 領先未部署的項目。
5. **斷線**：關掉 cloud-sql-proxy，確認 5433 無監聽。等你做決定的時候也先關，要用再連。

### 9.4 熱修通報

修到任何「正式機現行版本也有」的 bug，回報時必須寫「※ 此修復影響正式機，建議評估熱修上線」。判斷方式：git merge-base 比對 bug 引入點是否在正式機 tag 以前。起因：前一個專案有一個崩潰修好後在 main 躺了兩天沒人知道要部署，使用者在正式機踩到才發現。

### 9.5 上線節奏

建議**兩週一批**，不要累積一個月。每批都要走完 9.1〜9.3。累積越久，回退越難、登入後驗證越驗不完。

## 10. 上線後持續優化

### 10.1 夜間守衛（排程，每天凌晨）

Claude Code 排程任務每天 02:00 執行 .claude/skills/nightly-guard：

1. 看 main 有沒有新提交；沒有就結束。
2. 匯出 main 到隔離副本，跑三端全套單元測試＋lint＋整套 E2E。
3. **任何一題紅（包括單獨重跑會過的）→ 停：不併回任何東西、不前進狀態**，單獨重跑紅的那題分辨「每次都紅」或「偶發」，找出可能是哪個提交造成，寫報告給你早上看。
4. 全綠 → 更新 docs/test-baseline.md，看使用說明與示範影片有沒有過時（下一節），有就改、全綠就併回 main。
5. 報告第一行結論五選一：沒有新提交／全套全綠沒有要改的／已更新說明並併回／測試有紅暫停／有事要你決定。

### 10.2 使用說明與示範影片隨功能同步

- 每個畫面有說明條目，每件事有一份步驟（一件事只有一個名字、一份步驟），寫在前端程式裡、有測試擋錯字與過時。
- 開發對話改了畫面、按鈕、流程、方案差異，不自己重錄影片，在 PROGRESS.md 記「哪支說明或影片跟現況不一樣」。
- 夜間守衛全綠後才改說明、重錄影片，錄完抽格檢查字幕跟畫面對不對；字幕講的跟畫面寫的打架常是產品 bug 的線索。
- 影片放 GCS 不進映像檔，檔名帶內容指紋。

### 10.3 詞彙表與守衛測試

- docs/ui-terms.md 收「同一件事的唯一說法」與例外；前後端各有守衛測試擋舊說法。
- 規則說明寫完整句子，不用片語、括號補充、口語。
- 守衛測試還擋：真實公司資料、寫死埠號、不轉的載入圖示、禁止的時間寫法、Node 主版本不一致。

### 10.4 經驗要寫回 skill

出事故、踩到坑、找到更好的做法，你說「把這個放入 skill」，AI 就在 .claude/skills/dev-guidelines/SKILL.md 第 7 節加一條（日期、發生什麼、根因、之後怎麼做），並把做法改進寫回對應章節。不刪舊條目，過時的標「已由 ○○ 取代」。CLAUDE.md 只放短規則，skill 放做法與細節，兩邊衝突以 CLAUDE.md 與你當下指示為準。

### 10.5 覆蓋率怎麼看

- 每支後端路由必須被測試呼叫過且在契約裡，pre-commit 硬擋。
- 行覆蓋率只出報告、不設全域門檻；用途是找「整個檔案沒有任何測試碰到」的盲區。唯一門檻：新增的檔案不得零覆蓋。
- 不要為了衝百分比寫沒有斷言的測試。

## 11. 測試工具

一種工具跨前後端，學一次就夠。專案範本已內建設定。

| 工具 | 用途 | 用在 |

| Vitest＋Testing Library＋user-event | 前端單元與元件測試；互動一律 user-event | C |

## 12. 名詞解釋

| 名詞 | 白話解釋 |
|---|---|
| Prompt | 貼給 AI 的指令文字；手冊每步結尾的灰色方塊 |
| CLAUDE.md | 專案根目錄的規則檔，寫 AI 能動什麼、不能動什麼、用什麼指令驗證；Claude Code 每次開工自動讀 |
| skill | .claude/skills/ 底下的做法文件，Claude Code 會自動載入；dev-guidelines 是做法與踩坑紀錄 |
| 原型 | 可以點的畫面草稿，含系統說明、流程、欄位、測試資料，是需求基準 |
| 切片 | 一個使用者用得到的完整功能，從畫面到資料庫一次做完 |
| 切片原型 | 優化時只畫某個切片要改的畫面的小原型，存 docs/prototype/slices/ |
| 切片五步 | A 契約 → B 後端 → C 畫面 → D 合併 → E 驗收 |
| 拍板紀錄 | docs/decisions.md，每個決定一行一個 D 編號 |
| 模組 | 程式資料夾的單位，與切片不同 |
| 契約（OpenAPI） | 前後端的合約書 openapi.yaml，寫明每支 API 送什麼回什麼 |
| api-client | 從契約自動產生的程式，前台用它叫 API，契約改了型別檢查會紅 |
| 守衛測試 | 掃原始碼擋某種寫法的測試，例如擋真實公司名、擋寫死埠號 |
| 破壞性變更 | 新增必填、選填改必填、驗證變嚴、權限收緊、schema 改型別 |
| 回填腳本 | 把舊資料補成符合新規則的程式，試跑／--write 兩段式 |
| 事件時刻／業務日期 | 時間軸上的一個點（存 UTC、依觀看者時區顯示）／帳面上的日曆日（用業務時區算、全世界同一值） |
| 處理中四件事 | 反灰擋重入、轉圈、文字換「…中」、成功才關視窗 |
| 拋棄式環境 | verify-env.sh 起的一組臨時資料庫與前後端，用完刪掉 |
| 驗收等級 | 親驗（你用真帳號驗）／AI 自驗即可（AI 操作截圖、你事後看） |
| 夜間守衛 | 每天凌晨跑全套測試與 E2E 的排程對話 |
| 現況表 | deploy/部署說明.md 裡「正式機現在是哪一版」的表，部署當下更新 |
| 熱修 | 正式機也有的 bug，修好後單獨上線不等下一批 |
| 煙霧測試 | 部署後打幾支端點確認服務活著 |
| BFF | 自家後端代替瀏覽器跟 MCC 換通行證，通行證和密鑰都留在後端 |
| MCC | 公司會員中心 members.managers.center，負責登入 |
| OIDC | MCC 用的標準登入協定，跟「用 Google 登入」同一套 |
| sub | MCC 給每個會員的永久編號，當主鍵用，不用 email |
| Group／憑證 | MCC 用 Group 區分測試與正式，憑證兩套 |
| AUTH_MODE=mock | 假登入，只准本機與測試 |
| 401／403／404／422 | 沒登入／沒權限／找不到／資料格式錯 |
| Migration／Seed | 資料庫結構的版本記錄／預先塞入的範例資料 |
| CI | 每次推程式碼自動跑檢查的機器人；本手冊只用它做檢查，不做部署 |
| tag | git 的版本標記，prod/vN 打在正式機部署的 commit 上 |
| merge --no-ff | 合併時一定留一個合併提交，看得出哪一批是同一個切片 |
| 技術債 | 趕時間先將就的做法，記下來之後要還 |
