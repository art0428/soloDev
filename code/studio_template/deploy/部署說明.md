## 二、正式機現況表（唯一權威，每次部署當下更新）

這張表與 git tag `prod/vN` 一起是「正式機現在是哪一版」的權威。**部署當下更新、不拖**：晚更新的空窗會讓其他對話誤判正式機版本。懷疑表過期時以實況為準：`gcloud run services describe <服務> --region=<region> --format="value(status.latestReadyRevisionName)"`，migration 用 `npx prisma migrate status` 經 cloud-sql-proxy 查。

| 項目 | 值 |
|---|---|
| **最後部署** | <YYYY-MM-DD HH:mm（業務時區）>；版本 **prod/vN** ；一句話寫這版包含什麼 |
| 後端 revision | `<服務>-000NN-xxx`（image `backend:vN`；memory、timeout 若有改寫在這） |
| 前台 | bucket 版本或 CDN 失效時間；build 時燒進去的 API 網址 |
| 後台 revision（選配） | |
| **對應 commit** | `<sha>`（此 commit 以前的內容都已上線；全套關卡在隔離副本 `<sha>` 全綠：後端 N、前端 N、E2E N） |
| **tag** | `prod/vN` 打在上面那個 commit |
| **migration 高水位** | `<最後一支已套用的 migration 名稱>`（含）以前全部已套用；pending：無／<檔名>（破壞性，刻意留待下次，原因） |

## 三、每批上線的程序

逐條勾選版在 `deploy/release-checklist.md`，部署對話每次複製一份填。

### 3.1 部署前

1. 工作目錄乾淨且已 commit：`git status --short` 無輸出。
2. 動到那一端的全套測試全綠；夜間守衛最近一輪全綠（看 `docs/test-baseline.md` 最近一列與守衛報告）。
3. **臨場重查 pending migration**：起 cloud-sql-proxy，`DATABASE_URL=<正式庫連線> npx prisma migrate status`，**不可沿用舊盤點**。列出每一支 pending 是只新增還是破壞性。
4. **備份正式庫**：
   ```
   pg_dump "<正式庫連線>" --no-owner --no-privileges -f gcp/db/backup/backup_$(date +%Y%m%d%H%M%S).sql
   ```
   `gcp/db/backup/` 已 gitignore。確認檔案大小合理、表數對。
5. 列出這次要上的清單，每項標：migration 有無、是否破壞性、要跑的回填腳本、部署後要驗的功能。貼給使用者，**等允許再往下**。

### 3.2 部署順序

```
備份 → 只新增的 migration（migrate deploy）→ 部署後端 → 部署前台 → 部署後台（選配）→ 煙霧測試 → 登入後功能驗證 → 打 tag → 更新現況表 → 斷線
```

- **破壞性 migration（刪欄、刪表、改型別）順序相反**：先部署程式、確認穩定（至少煙霧測試過），再跑 migration。否則舊 revision 還在讀那一欄會 500。順序寫在那支 migration.sql 的檔頭，照檔頭做。
- `prisma migrate deploy` 只套本地目錄裡有、資料庫沒有的 migration；**migration 目錄沒進 commit 它會印 `No pending migrations` 並 exit 0**，看起來正常、程式一上線就爆。所以 3.1 第 1 點不可省。
- 套完要自己驗：`npx prisma migrate status` 顯示 up to date，不要只看 exit code。
- 前台的 API 網址是 build 時燒進去的，改網址要重新 build。
- 回填腳本在部署後手動跑：先不帶參數試跑看數字，貼給使用者，允許後 `--write`。

指令：

```
# 後端 build + push（在 repo 根目錄跑；只建映像不部署，tag 已存在會直接失敗）
# 上傳哪些檔由 .gcloudignore 決定，要確認就跑 gcloud meta list-files-for-upload
gcloud builds submit --config deploy/cloudbuild.yaml --substitutions=_TAG=vN .

# 只新增的 migration（經 cloud-sql-proxy）
DATABASE_URL='<正式庫連線>' pnpm --filter backend run prisma:migrate
DATABASE_URL='<正式庫連線>' pnpm --filter backend run prisma:status

# 部署後端。變數名稱見 deploy/env/.env.prod.example：[env] 段用 --set-env-vars、[secret] 段用 --set-secrets。
# 第一次要帶齊；之後不帶 --set-env-vars 就沿用現行，只用 --update-env-vars 改 APP_VERSION，/health 才看得出上的是哪一版。
gcloud run deploy <專案名>-api --image <region>-docker.pkg.dev/<專案>/<專案名>/backend:vN \
  --region <region> --platform managed --allow-unauthenticated \
  --service-account <專案名>-run@<專案>.iam.gserviceaccount.com \
  --add-cloudsql-instances <專案>:<region>:<實例> \
  --update-env-vars APP_VERSION=prod/vN \
  --set-secrets "DATABASE_URL=DATABASE_URL:latest,SESSION_SECRET=SESSION_SECRET:latest,MCC_CLIENT_SECRET=MCC_CLIENT_SECRET:latest,MCC_GROUP_JWT=MCC_GROUP_JWT:latest"

# 前台 build（[build] 段的變數會燒進靜態檔）並上傳
VITE_API_URL=<API 網址> VITE_APP_NAME=<專案名稱> pnpm --filter front run build
gcloud storage rsync front/dist gs://<bucket> --recursive --delete-unmatched-destination-objects
gcloud compute url-maps invalidate-cdn-cache <url-map> --path "/*"
```

後台（選配）目前範本沒有附，前台上線後要做時再照後端的做法補 `deploy/Dockerfile.admin` 與對應的 cloudbuild 設定。

### 3.3 部署後

1. **煙霧測試**：`bash backend/scripts/smoke-test.sh <API 網址> <前台網址> prod/vN`。只做免登入、唯讀、不留痕跡的檢查：`/health` 200、`AUTH_MODE` 不是 mock、`/health` 回的版本就是這次的 `prod/vN`、未登入打 `/api/me` 回 401、壞 JSON 回 400、前台首頁 200。
2. **登入後功能驗證**：煙霧測試看不到登入後的畫面崩潰。使用者在瀏覽器完成 MCC 登入（登入不自動化），之後由部署對話操作這次上線的每個功能走一遍、截圖回報。
3. **打 tag**：`git tag prod/vN <部署的 commit>`，push tag 等使用者指示。tag 是正式機版本的第二權威。
4. **更新第二章現況表**，當下更新。
5. **斷線**：關掉 cloud-sql-proxy（`kill <pid>`），`lsof -nP -iTCP:5433 -sTCP:LISTEN` 確認無監聽。中途等使用者做決定時也先關，要用再連（起一次 2 秒）。gcloud 登入狀態是憑證不是連線，不必登出。

### 3.4 熱修

修到任何「正式機現行版本也有」的 bug，回報時必寫「※ 此修復影響正式機，建議評估熱修上線」。判斷：`git merge-base --is-ancestor <bug 引入 commit> prod/vN` 為真。熱修一樣走 3.1 至 3.3，tag 升小版號。

### 3.5 回退

- 程式回退：`gcloud run services update-traffic <服務> --to-revisions <上一個 revision>=100`。
- 只新增的 migration 不必回退，舊程式不讀新欄位。
- 破壞性 migration 執行後要回退，用那支 migration.sql 檔頭寫的回退語句先把欄位加回來，再切流量。
- 資料回退用 3.1 第 4 點的備份，`psql "<連線>" -f <備份檔>`，**這是刪除性操作，一定先問**。

## 四、上線節奏

兩週一批，不累積一個月。每批都走完 3.1 至 3.3。累積越久，回退越難、登入後驗證越驗不完。

## 六、首次建置（只做一次）

每一步做完回填第一章速查表。

1. **GCP 專案與 API**：`gcloud services enable run.googleapis.com sqladmin.googleapis.com secretmanager.googleapis.com artifactregistry.googleapis.com cloudbuild.googleapis.com storage.googleapis.com`。
2. **Cloud SQL**：建實例（或用既有的）、建資料庫 `<專案名>`、建專用帳號；密碼用 `openssl rand -hex 24`（hex 沒有 URL 特殊字元，連線字串才不會解析失敗）。
3. **Secret Manager**：`DATABASE_URL`、`SESSION_SECRET`（`openssl rand -base64 48`）、`MCC_CLIENT_SECRET`、`MCC_GROUP_JWT`。值由使用者自己貼進 gcloud 指令，**不經過對話**。
4. **Artifact Registry**：`gcloud artifacts repositories create <專案名> --repository-format=docker --location=<region>`。
5. **服務帳號**：`<專案名>-run@<專案>.iam.gserviceaccount.com`，給 Cloud SQL Client 與 Secret Accessor。
6. **後端第一次部署**：先 `gcloud builds submit --config deploy/cloudbuild.yaml --substitutions=_TAG=v1 .` 建出 `backend:v1`，再照 3.2 的 `gcloud run deploy`，第一次要帶齊 `--set-env-vars`（`deploy/env/.env.prod.example` 的 [env] 段每一個）與 `--set-secrets`。容器的 `NODE_ENV`、`HOST`、`PORT`、`TZ` 由 `deploy/Dockerfile.backend` 設好，不要再帶。
7. **前台**：建 bucket、設網站模式、建 Cloud CDN 與 HTTPS 負載平衡器、綁網域。
8. **MCC 登記**：向 MCC 管理者取得正式 Group 憑證，正式 redirect_uri 登記白名單。
9. **第一次 migration 與 seed**：`migrate deploy`；正式機**不跑**示範世界的 seed。
10. **煙霧測試、登入後驗證、打 `prod/v1`、填現況表、斷線**。
